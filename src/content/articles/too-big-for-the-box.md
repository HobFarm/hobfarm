The Wonder Machine has learned how to do nothing.

That sounds like the least impressive feature ever added to a game. It took an embarrassing amount of effort.

In the current test world, submitting a blank command does not move the clock, choose an action, trigger an event, or smuggle a decision through the side door. It returns no action. If the player decides to wait, that is different. Waiting is explicit. It belongs in the record. Time may pass. An opportunity may open or close. The same seed and the same action sequence must still produce the same result when the session is replayed.

This is the kind of problem I now consider important.

The problem is not how to make a language model say something enchanting. Language models can produce enchanted wallpaper by the mile. The problem is deciding which machine is allowed to make a fact true. Where does the world live? Which part can change? Which part must remain fixed? What survives when a provider changes a model, a browser closes, a service disappears, or I forget why I made a rule six months earlier?

I had been staring at these boundaries when I looked at the old *Civilization V* disc on my desk and understood that the game had become too big for the box.

Not too many gigabytes. That is the easy reading, and it is not the one I mean. The game had become too distributed for the box to describe. The disc was physical evidence of a system whose activation, updates, account, downloadable content, multiplayer, saves, patches, and future compatibility already extended beyond the plastic case. The box still looked like the object. It was becoming a terminal.

We have been here before.

## 1. The machine that waits

Wonder Machine is the runtime I am building for Other Alice. It is not a deployed public cloud game. It is not an omniscient storyteller. It is not an AI that owns a world and improvises consequences while code politely takes notes.

The current boundary is much duller and much more useful. Grimoire owns the authored material. A compiler turns an explicit selection of that material into a world pack. The pack is immutable during play. Wonder Machine creates a mutable session from it. Deterministic code owns state changes, eligibility, time, routes, seeded outcomes, saves, and replay. An optional language layer may help map a grounded phrase onto an action the code already permits. A narrative layer may describe the result the code already reached. Neither gets to invent a destination, slip an object into inventory, rewrite the pack, or decide that silence means wait.

This is not an aesthetic preference. It is how the machine remains an inspectable game instead of a séance.

The lesson arrived through failure. Blank input sounds trivial until a conversational interface begins treating absence as an invitation. A model wants to be helpful. A game engine needs to know whether the player acted. If those are the same system, the helpful instinct can alter the world. If they are separate, the model can offer language while the runtime retains authority.

That separation is also a miniature of the whole technological arrangement now forming around us. The device in front of me may display the world. It does not follow that the world lives there. The visible response may sound decisive. It does not follow that the response owns the truth. The screen is where the arrangement becomes legible, not necessarily where the work happens.

The oldest computer games understood this because they had no other choice.

## 2. The disc on my desk

I bought *Civilization V* on disc. I still have it. That fact has become more interesting than the object itself.

Valve announced in May 2010 that [every PC version of *Civilization V* would use Steamworks](https://store.steampowered.com/oldnews/3792), including product activation, automatic updating, achievements, downloadable content, multiplayer, and access from supported computers. The disc carried data, but it did not contain the whole relationship. The relationship included a service.

I did not experience this as a philosophical crisis. I installed the game and lost years to it. I have already written about the peculiar afterlife of that disc and the accumulating friction between an old game, a newer computer, an operating system, launchers, drivers, accounts, and my available hours in [Everything Is Still Loading](/articles/everything-is-still-loading/). I have also written about what happened when maintaining my own complicated system replaced playing someone else's in [I Could Be Playing Civilization](/articles/i-could-be-playing-civilization/).

The disc still has emotional authority. It is a thing I can hold. Its art tells me what it contains. It remembers a purchase more cleanly than an account ledger does. If the network is down, the case remains on the shelf looking confident.

But physical presence and operational completeness are different properties. The plastic can survive while the path from plastic to play accumulates dependencies. A package may carry an installer but require an account. It may carry most of a game but expect day-one patches. It may carry a license token, or nothing but a code. It may install a client whose most consequential state lives somewhere else.

The box becomes a diagram with important arrows omitted.

That does not make physical media worthless. It makes the old promise harder to keep: the promise that the purchased object is enough. I prefer a disc to an expiring listing. I also know that the disc on my desk already belonged to a hybrid age.

## 3. The terminal is not the world

Before the home computer made the machine feel personal, a screen and keyboard could be the near end of a much larger arrangement.

Will Crowther wrote the first version of *Adventure* in 1975 in FORTRAN on a PDP-10 timesharing system. The [Computer History Museum's account](https://www.computerhistory.org/revolution/computer-games/16/190) connects its caves to Crowther's caving experience and its fantasy to *Dungeons & Dragons*. Don Woods found the program, obtained permission to expand it, and helped turn it into the work that spread through universities and laboratories. Copies also traveled across ARPANET-connected hosts.

That last sentence needs its boundaries. It does not mean every early player sat directly on ARPANET. A terminal might be attached locally, reached through a dial-up connection, or connected through a networked host. Access varied by institution and period. The useful point is simpler: the player's terminal could be somewhere other than the computer holding the running world.

At MIT, the game that became *Zork* grew on a PDP-10 running ITS. Tim Anderson's participant history describes a mainframe work assembled from rooms, objects, verbs, parsers, and rules, then encountered by local and remote users. The authors were not fumbling toward software by accident. They were experienced programmers working within hard memory and machine constraints, building a language interface sophisticated enough to make the computer feel like a place.

I traced more of this lineage in [Take Me to Phobos](/articles/take-me-to-phobos/): from *Adventure* and *Zork* to bulletin boards, home computers, graphical worlds, and the recurring dream of entering a remote system through an ordinary machine. What matters here is the geography. A game could be played in front of you while living somewhere else.

Calling these games primitive mistakes the size of the display for the size of the idea. *Adventure* had geography, objects, state, rules, memory, humor, danger, and a parser. *Zork* deepened the model and the conversation. A line of text was not the world. It was a narrow opening onto a world represented elsewhere.

That is what a terminal does. It compresses a system into the amount of surface a person can use.

## 4. The machine that fit inside another machine

The mainframe world had a problem: the mainframe was not coming home with the player.

Infocom's answer was to split the work. Instead of rewriting the whole game for every home computer, the company compiled story files for a virtual machine. Each target computer needed an interpreter for that machine. The story could then travel across different hardware in a compact, controlled form. The descendants of that design are documented in the [Z-machine standards](https://www.inform-fiction.org/zmachine/standards/).

This was a spectacular reversal. The large host game became a portable machine inside smaller machines.

It also clarified a distinction that keeps returning in my work: content is not state, and state is not presentation. Rooms, objects, vocabulary, and rules can be packaged separately from the interpreter. The interpreter can run on machines with different displays and operating systems. A save records the particular world a player has changed. The prose is what the player sees, but prose alone is not what makes the game consistent.

Home computers and consoles made the local box feel sovereign. The program arrived on tape, cartridge, floppy, optical disc, or hard drive. The machine under the desk performed the simulation. The television or monitor showed it. For a while, this arrangement encouraged a powerful and mostly accurate intuition: the game is here.

Even then, the object was never merely its storage medium. A cartridge needed compatible hardware. A disc needed a drive, an operating system, and executable code that still behaved. But the dependencies were close enough to see. The player could point to the shelf and the machine and reasonably say, there it is.

The achievement of physical software was not that it eliminated systems. It brought enough of the system into one room that the boundaries felt like an object.

Now those boundaries are spreading out again.

## 5. The box empties

The disappearance of a disc does not prove that a game is remotely rendered. A download can still install a game that runs locally. A code in a box is not evidence that the GPU lives in a data center. Storage, execution, authentication, and distribution are separate questions.

This distinction matters because one of the easiest ways to make a technology essay sound impressive is to collapse every dependency into “the cloud.” That would be false.

What we can document is narrower. *Civilization V* tied every PC copy to Steamworks in 2010. Rockstar's current support page says the [physical version of *Grand Theft Auto VI* contains a download code and no disc](https://support.rockstargames.com/articles/4QfG4FmZCf5W1gS8jy4UVT/grand-theft-auto-vi-platform-editions-and-versions). Sony has announced that [physical disc production for new PlayStation-console releases will end in January 2028](https://blog.playstation.com/2026/07/01/physical-disc-production-ending-in-january-2028-for-new-games-releasing-on-playstation-consoles/), while previously released physical games remain unaffected.

Those facts do not say that *GTA VI* was too large for a disc. Rockstar does not make that claim in the cited support material. They do not say the game is cloud-rendered. The facts say the physical edition is a code in a package, and that a major console platform has put an end date on producing discs for new releases.

The package is not necessarily gone. Its old function is.

A box used to transport executable material. Then it became one part of an installation and account system. Now it can carry a code that instructs a remote service to authorize a download. The object remains useful as a gift, a retail signal, a collector's artifact, or a durable reminder that a purchase occurred. But it cannot restore the missing service by itself.

The old box held the game imperfectly. The new box can point at the game perfectly and hold almost none of it.

## 6. The room behind the screen

The phrase “the cloud” hides physical specificity. There is no single sky computer. There are server racks, storage systems, databases, fiber routes, content caches, power contracts, cooling systems, operations teams, access policies, and machines failing one at a time.

Cloudflare describes a network spread across [hundreds of cities](https://www.cloudflare.com/network/). That does not make the network a global mainframe in any exact architectural sense. A mainframe is a particular class of computer. A distributed service is many systems arranged to appear coherent from the outside. The resemblance is experiential: a modest terminal opens onto computation and state held somewhere the user does not control.

The room behind the screen is also a room with a power bill. The International Energy Agency's central projection puts global data-center electricity consumption at about 485 terawatt-hours in 2025 and around 950 terawatt-hours in 2030, with substantial uncertainty and local bottlenecks. AI-focused facilities are expected to account for much of the growth. These are projections, not an energy destiny. They are enough to puncture the fantasy that remote computation has no body.

Every time an interface becomes lighter, infrastructure becomes easier to forget. A terminal can look like a blank rectangle because the machinery has been moved out of sight. The service can feel instantaneous because copies, caches, and routes were built before the click. The model can feel like a mind in a textbox because training clusters, inference hardware, safety systems, data pipelines, and billing all arrive as one conversational surface.

This arrangement is not automatically bad. It gives a one-person publisher access to capabilities that once required a company. It lets me store media without filling the website repository, deploy functions near readers, and ask a coding agent to inspect a project large enough that I can no longer hold every file in working memory.

It also means my workshop includes rooms I rent and cannot enter.

That changes the meaning of ownership. I can own my source files while depending on a provider to build, serve, interpret, or execute them. I can possess the design of a world while renting the machinery that makes one version of it visible. The source of truth and the source of operation may be different places.

## 7. An apprenticeship with no master

I did not become a software engineer before using AI to build software. I began building, then tried to learn fast enough to understand what the build required.

That order is dangerous. It is also what happened.

The useful part of AI-assisted work has not been that the machine “does it for me.” The useful part is that I can put an unfamiliar system under examination immediately. I can ask why a route failed, inspect the answer against the repository, run the test, watch the test expose the answer, revise the rule, and repeat. The feedback loop is close enough that concepts stop being abstract.

I have learned about content schemas because invalid frontmatter broke builds. I learned about deterministic randomness because a replay that changes is not a replay. I learned about ownership boundaries because two repositories both believed they owned the same world. I learned that a saved session cannot safely contain every authored object by accident. I learned that “no input” and “wait” are different because a conversational layer wanted to turn silence into activity.

This is an apprenticeship without a stable master. The model can explain a concept and hallucinate the local implementation in the same paragraph. It can produce a correct patch for the wrong repository. It can be brilliant about the language and oblivious to the business. The only durable teacher is the combination of source, test, failure, documentation, and repeated contact with the actual system.

That is why the maintenance described in [I Could Be Playing Civilization](/articles/i-could-be-playing-civilization/) is not peripheral to the work. The instruction files, source-of-truth rules, test fixtures, and validation commands are part of the apprenticeship. They make correction accumulate. [A World of Geniuses Needs a System](/articles/a-world-of-geniuses-needs-a-system/) is my longer argument for that structure: intelligence without a durable way to preserve decisions keeps rediscovering the same room.

The model can accelerate the encounter. It cannot take responsibility for what I fail to understand.

## 8. The real dark factory

“Dark factory” is an alarming name for a serious engineering question: if agents write the code, what replaces the human habit of reading it?

StrongDM's public description of its [software factory](https://www.strongdm.com/blog/the-strongdm-software-factory-building-software-with-ai) says humans define intent, scenarios, and constraints; agents generate and iterate; validation replaces code review. The company's Digital Twin Universe imitates the external services its software depends on so scenarios can be exercised without hammering live systems.

Simon Willison's account of a demonstration adds the details that make the claim interesting. Scenarios can function like holdout sets, kept outside the implementation the coding agents see. The system is judged by observed trajectories through those scenarios, not only by whether an agent-written unit test says `true`. The digital twins reproduce relevant behavior from services such as Okta, Jira, Slack, and Google products. At the time of the demonstration, the lab itself was a three-person team of experienced developers.

This is not “five prompts to a fortune.” It is a relocation of engineering labor. People specify the world in which the software must prove itself. They construct the harness, the scenarios, the simulations, and the measures. They decide what failure means. They absorb the cost. Willison called attention to the reported standard of spending at least $1,000 a day in tokens per human engineer and asked the obvious economic question: what kind of software business can sustain that factory?

I cannot verify StrongDM's internal performance from a public blog post. The company description is a participant claim. The important thing is that it exposes a testable theory of work. It names inputs, constraints, validation, cost, and observable behavior. It creates surfaces on which the promise can fail.

The dark factory is not dark because nothing happens inside. It is dark because code stops being the primary surface where a human looks for confidence. The lights move to the scenarios, the observed behavior, and the record of failure.

## 9. The bullshit factory

My Instagram feed contains another kind of factory.

One public post says an automated business can make $15,000 a month. Another says Claude found the reason an account was not growing and added one million in reach and 7,000 followers. Another says seven prompts helped produce 194,000 followers. Other supplied posts promise $2,000 a day on Pinterest, $5,767 a month from Claude plus Instagram, “unlimited” non-follower reach from duplicate reels, or 2.5 million views in 28 days from five prompts.

The posts are real. The displayed outcomes are claims.

I have not audited the accounts' revenue, costs, prior audiences, attribution windows, ad spending, client work, affiliate income, or failed attempts. I do not know whether each claim is accurate. I do not have evidence that every person making one of these posts is dishonest. A screenshot is a receipt for what appeared on the screen, not a receipt for the business behind it.

The bullshit factory is not defined by being wrong. It is defined by making the wrongness difficult to establish.

It presents the output without the scenario. There is no denominator. The audience sees the successful account but not the population of people who copied the prompt. It sees revenue without costs, growth without the starting point, automation without setup, a time window without the years that may have preceded it, and a result without a stable way to reproduce it. The missing context is not a bug in the message. It is what lets the message travel.

The product is often not the automated business. The product is the distance between the claim and the evidence.

## 10. The millionaire-copy machine

An Entrepreneur contributor article published July 24, 2026, announces that [AI is quietly creating millionaires and shows readers “exactly how to copy them”](https://www.entrepreneur.com/building-a-business/ai-is-quietly-creating-millionaires-and-heres-exactly-how-to-copy-them-no-staff-no-code). Its key takeaways include stories labeled $80 million, $40 million, and $400 million. The article routes readers toward an AI Success Kit and a book.

One of those numbers has a public receipt. Wix announced that it acquired Base44 for $80 million in initial consideration, with additional retention bonuses for employees. That is a real transaction. It is not evidence that a reader can reproduce the outcome by copying a tool stack.

The acquisition also restores the middle that the millionaire-copy frame compresses. There was a company, a founder, a team, employees important enough to receive retention payments, a buyer with strategic reasons, a product, usage, timing, negotiation, and risk. “No staff, no code” is a headline arrangement. The deal itself had people in it.

This is where an individually true number can support a structurally false lesson. Base44 sold. Therefore AI creates millionaires. Therefore the reader can copy them. Therefore the next step is to enter the funnel.

The logical joints are doing more work than the facts.

The same compression appears in the social posts. A model becomes the agent responsible for an outcome, while the person's existing audience, sales ability, offer, production history, editing, advertising, and selection disappear. The claim gets cleaner as the work gets less visible. Claude reviewed the account. Claude created the content. Claude made the money. The human becomes a before picture holding a laptop.

This is not praise for the model. It is a way to remove labor from the story so the method can fit in a caption.

The dark factory also hides code. Its difference is that it makes the hidden work answer to a specification. The millionaire-copy machine hides the work so the promise looks transferable.

## 11. The economically wrong machine

HobFarm is not evidence that AI has solved capitalism.

I have spent thousands of dollars and an unreasonable number of hours building a publishing site, article archive, gallery, product structure, knowledge system, game runtime, story world, and the instructions required to stop all of those things from eating one another. The project has produced little or no money.

By the logic of the income posts, this is a failed use of AI. It may be.

The system has taught me more than it has earned. It has left behind source files, tests, diagrams, articles, and a growing understanding of where my work lives. Those are real outcomes. They do not become revenue because they are real. A technically coherent system can still be an economically wrong machine.

I need to preserve that sentence because AI culture is eager to erase both sides of it. The sales culture says that powerful tools should produce effortless income. The contempt culture says that anything made with the tools is slop. Both replace looking with a category.

I have argued [Against Slop](/articles/against-slop/) as a term that often dodges the actual criticism. I have tried to say [How to Fix Slop](/articles/how-to-fix-slop/) by restoring intention, selection, revision, specificity, and the willingness to discard. In [How Psychedelia Went Beige](/articles/how-psychedelia-went-beige/), I looked at what happens when a style that once carried risk becomes a safe surface effect. The same problem applies here. A machine can multiply surfaces faster than a person can decide what deserves to exist.

The solution is not to pretend the multiplier is a business.

I am building something primitive, expensive, and currently difficult to explain. It may never support itself. That uncertainty is not a hidden testimonial waiting for the success chapter. It is the present economic fact.

The creative fact is different: without the current tools, I would not have reached this particular machine. I would also have avoided many mistakes the tools helped me make faster. Both are true.

## 12. Alice does not need more content

Lewis Carroll's *Alice's Adventures in Wonderland* and Bram Stoker's *Dracula* are available as public-domain texts in the United States. That gives me source material I can read, quote within an editorial purpose, transform, annotate, and build from without borrowing the inventions of a modern film, game, or television adaptation.

Public domain does not make the work automatic. It makes the raw relationship possible.

Other Alice began with my own characters, story logic, visual development, and the recurring problem of how to let a player enter a literary world without turning the world into a bag of references. The original Alice is useful because it understands doors, size, appetite, language, authority, and curiosity. *Dracula* is useful because it understands documents, distance, pursuit, thresholds, and the slow assembly of knowledge. Neither needs a chatbot pasted on top.

In [It's Gonna Be Different Every Time](/articles/gonna-be-different/), I described a scene in which Big waits. The model was allowed to describe a code-owned outcome, not decide what the outcome should be. That distinction now reaches deeper into the runtime. Waiting must be explicit. The opportunity must be eligible. The route must exist. The destination must be in the pack. The seed must preserve the outcome. The save must restore it. Replay must not produce a more poetic version of history.

This sounds restrictive because the fashionable promise is infinity. Ask anything. Go anywhere. Every playthrough becomes a new universe.

Infinity is cheap language. A good door is expensive.

A door needs a place on each side. It needs conditions. It needs a reason to be closed and a consequence for opening. It needs to know whether the player knocked, waited, walked away, or submitted an empty field. It needs a world stable enough that curiosity can become knowledge.

Alice does not need more generated content. She needs the first door to work.

## 13. The bounded Wonder Machine

The current Wonder Machine boundary can be drawn without magic.

Grimoire contains authored knowledge and private story material. A compiler selects and validates an explicit pack for the runtime. Wonder Machine consumes the pack without reaching back into the authoring repository. During play, the pack stays immutable. A session changes.

The session knows the player's location, inventory, flags, clocks, eligible routes, and event history. Named random streams produce seeded outcomes. A save captures what is required to restore the session. A replay records enough ordered action to reach the same result again. The runtime rejects an effect or destination that is not grounded in the pack.

The language layer has a narrow job. It can map a phrase onto an allowed action when the reference is grounded and sufficiently clear. If the input is ambiguous, refers to no object, or requests an invalid action, the runtime can refuse it. The narrative layer can turn the resulting event into prose. It cannot retroactively make its prose true.

This architecture does not guarantee a good game. It guarantees that certain kinds of failure have somewhere to be caught.

If the world pack changes during play, the boundary failed. If blank input advances the clock, the input rule failed. If a model invents an exit, the adapter failed. If the same seed and action sequence produce a different event, determinism failed. If a save cannot restore the session or a replay cannot reconstruct it, persistence failed.

Those failures are less glamorous than a model generating a surprise character. They are also the difference between a surprise and a contradiction.

The Wonder Machine remains developing software. Its current test worlds and private integrations are not proof of a finished public game. The diagram describes a real boundary in the repositories, not a claim that Wonderland is already running in the cloud.

## 14. Wearable terminals

The next terminal may look less like a computer because the computer will be easier to place somewhere else.

Meta's May 2026 developer preview for [display glasses](https://developers.meta.com/blog/build-for-display-glasses/) describes mobile and web paths for small applications using a display, audio, camera, phone location, motion, local storage, and Neural Band gestures. The company also describes games and streaming as possible uses. Its earlier Orion device is explicitly a product prototype for employees and selected external audiences, not a consumer product people can buy.

NVIDIA's [CloudXR](https://developer.nvidia.com/topics/ai/xr/cloudxr-sdk) supplies another piece of the arrangement: render a spatial experience on powerful remote GPU resources, encode it, and stream it to a lighter AR, VR, or browser client. This is an available technical pattern, not evidence that a particular pair of glasses will run Wonder Machine or that remote rendering solves latency, cost, comfort, battery, privacy, or access.

Still, the direction is legible. A wearable can become a terminal. It can collect a gesture, show a layer, play a voice, and maintain the illusion that the world is in the glass. The state may live on a phone. The rendering may live on a nearby computer. The simulation may live in a service. Assets may arrive from a content network. Identity may come from another provider. The little terminal can open one world assembled across many machines.

This is the PDP-10 arrangement returned with better optics and vastly more complicated terms of service.

The exciting possibility is not a screen pasted onto reality. It is continuity. A story world can remain itself while changing terminals. I could enter at a desktop, continue on a phone, hear a character through glasses, and return later to a saved session. The world would not need to regenerate itself for every surface. The terminal would ask the same runtime what is true.

The frightening possibility is identical. If every terminal depends on rented identity, rented inference, rented rendering, rented storage, and rented distribution, the world can be everywhere and possess no place where it can continue alone.

Portability used to mean making the machine small enough to bring home. It may now mean making the world's contract explicit enough to move between hosts.

## 15. The first door

Provider terms make an important distinction between ownership and control.

The current OpenAI Services Agreement says that, as between the customer and OpenAI and to the extent permitted by law, the customer retains input rights and owns output; OpenAI assigns any rights it has in that output. The same agreement makes the customer responsible for evaluating accuracy and appropriateness, allows service updates, and describes circumstances in which access may be limited or suspended.

Cloudflare's self-serve agreement grants a limited, revocable right to use its services. It also reserves suspension and termination powers and permits future agreement changes. These are ordinary service terms, not evidence that either provider is plotting to confiscate my rabbit.

They do mean the infrastructure is not mine.

Ownership of model output is also not the same as copyright protection. The U.S. Copyright Office's 2025 report says prompts alone generally do not provide enough human control to make the user the author of the output under current technology. Human-authored selection, arrangement, expressive input, and modification may be protected, depending on the facts. Assistive use does not erase copyright in the human work.

That is another reason to keep the world in explicit human-authored sources and deterministic code. It is good engineering. It also leaves a clearer record of what I designed, wrote, selected, arranged, revised, and approved.

I made the broader dependency argument in [You Do Not Own the AI You Pay For](/articles/you-do-not-own-the-ai-you-pay-for/). Subscription access is not possession. A provider can change models, prices, limits, policies, regions, or products. The practical answer is not purity. I cannot build this project without dependencies. The answer is to know which dependency is allowed to hold which part.

The article lives in a Markdown file. The evidence ledger lives beside the project. The images have checksums. The world pack can be rebuilt from authored sources. A session can be saved and replayed. The runtime can run without giving a language model authority over state. The current cloud can serve the public work, but the public work does not exist only as a response trapped inside the cloud.

This is not independence. It is an escape route.

The first computer-game worlds were too large for the terminal because the terminal was never the world. Then software entered the home and made the world feel like an object. The object emptied into accounts, downloads, services, and distributed machines. Now language models and wearable terminals promise worlds that can surround us without revealing the room where they run.

I am building the opposite of an infinite world.

I am building one primitive door with an address on each side. The player may open it, ignore it, leave, return, wait, or do nothing. The machine must know the difference. The pack must remain what was authored. The session must remember what happened. The model may describe the light under the threshold. It does not get to decide that the door was always open.

Beyond it is Wonderland, eventually.

For now, the door is enough.
